Relational Database Structure

The system is designed with strict relational constraints, optimizing indexing, cascade configurations, and primary/foreign keys.

Physical Entities Overview

  • Primary Keys (PK): Unique identifiers, auto-incrementing integers, enforced on every table.
  • Foreign Keys (FK):
    • `lost_items.user_id` → `users.user_id` (CASCADE on delete)
    • `lost_items.category_id` → `categories.category_id` (RESTRICT on delete to prevent orphans)
    • `claims.lost_id` → `lost_items.lost_id` (CASCADE)
  • Unique Constraints: `users.email` (prevent duplicate registrations) and composite unique key `match_suggestions(lost_id, found_id)`.

DDL Primary/Foreign Enforcements

CREATE TABLE lost_items (
  lost_id INT AUTO_INCREMENT,
  user_id INT NOT NULL,
  category_id INT NOT NULL,
  CONSTRAINT pk_lost_items PRIMARY KEY (lost_id),
  CONSTRAINT fk_lost_items_user 
    FOREIGN KEY (user_id) REFERENCES users(user_id) 
    ON DELETE CASCADE,
  CONSTRAINT fk_lost_items_category 
    FOREIGN KEY (category_id) REFERENCES categories(category_id) 
    ON DELETE RESTRICT
);

Normal Form (1NF → 2NF → 3NF) Proofs

1. First Normal Form (1NF)

Rule: All column cells must contain atomic values (no lists, no repeating groups). We must have a Primary Key.

Proof in our DB: Colors and keywords are strings, categories are atomic integers, not comma-separated lists. Every row contains a unique PK (`user_id`, `lost_id`, etc.).

2. Second Normal Form (2NF)

Rule: Must be in 1NF, and all non-key columns must depend on the *entire* Primary Key (No partial dependency on composite keys).

Proof in our DB: Our primary keys are single columns (auto-incrementing integers). This automatically eliminates partial dependencies because there are no composite primary keys, keeping non-key fields bound directly to the single PK.

3. Third Normal Form (3NF)

Rule: Must be in 2NF, and no non-key columns can depend on other non-key columns (No transitive dependencies).

Proof in our DB: Items only save `category_id` and `location_id`. The names and descriptions of categories or locations are stored in separate tables (`categories`, `locations`). If they were stored in `lost_items`, it would create a transitive dependency (e.g. `lost_id → category_id → category_name`). Splitting them satisfies 3NF.

Triggers, Transactions & Stored Procedures

This system utilizes advanced MySQL 8.0 procedural logic to automate matches and execute transactions.

Transactions & Stored Procedures

When a claim is approved, the system starts a transaction. Multiple statements must succeed together:

  1. Update claim row to `approved`.
  2. Update the matching Lost Item to `returned`.
  3. Update the matching Found Item to `returned`.
  4. Generate notifications and log the action.

If any update fails, MySQL executes the `EXIT HANDLER` and rolls back the changes to maintain ACID properties.

Procedure Code Draft

CREATE PROCEDURE sp_ApproveClaim(IN p_claim_id INT, ...)
BEGIN
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;
  END;

  START TRANSACTION;
  -- Updates claims, items, inserts audit log
  COMMIT;
END;

Auto-Matching Triggers

When a student files a lost or found report, a trigger executes `AFTER INSERT`. It runs a similarity query comparing:

  • Category (40% match weight)
  • Location (20% match weight)
  • Color (20% match weight)
  • Title overlap (20% match weight)

If the total score is ≥ 50, it logs a row in `match_suggestions` and sends notifications immediately.

Trigger Code Draft

CREATE TRIGGER trg_lost_items_match 
AFTER INSERT ON lost_items FOR EACH ROW
BEGIN
  INSERT INTO match_suggestions
  SELECT NEW.lost_id, found_id, 
         (category_score + loc_score + color_score)
  FROM found_items
  HAVING score >= 50;
END;

Top Viva Questions and Answers

Q1. What is the difference between a Trigger and a Stored Procedure?

Answer: A stored procedure must be explicitly called by the application using `CALL procedure_name(...)`. A trigger is executed implicitly by the DBMS in response to a DML event like `INSERT`, `UPDATE`, or `DELETE` on a specific table.

Q2. How is transaction integrity (ACID) maintained during claim approval?

Answer: We wrap the operations in `START TRANSACTION` and `COMMIT` blocks inside `sp_ApproveClaim`. If any update violates foreign keys or fails, MySQL triggers a rollback via the `DECLARE EXIT HANDLER FOR SQLEXCEPTION`, reverting all tables to their initial state to ensure consistency.

Q3. Why did you use Views in your Dashboard statistics?

Answer: Views like `vw_monthly_statistics` encapsulating complex subqueries simplify our backend code, improve security by hiding base tables, and run efficiently because the SQL query planner caches the view definition.

Q4. Explain how your Audit Logging system works.

Answer: We have triggers defined `AFTER INSERT`, `AFTER UPDATE`, and `AFTER DELETE` on core tables. Whenever a change occurs, the trigger inserts a row containing the user ID, timestamp, operation type, table name, and a JSON dump of the old/new values using MySQL's native `JSON_OBJECT()` functions.
